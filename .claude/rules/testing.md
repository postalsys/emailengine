## Testing

- Uses Node.js native test runner with native assert module
- Both tiers are sequenced by `test/run-tests.js`, which flushes Redis, boots a live server when the tier needs one, and shells out to `node --test`. No build tool and no test-runner devDependency is involved
- Uses Redis database 13 for test isolation (`config/test.toml`). `NODE_ENV=test` must be set before `@zone-eu/wild-config` loads, otherwise the development database is flushed instead - the npm scripts set it, and `test/run-tests.js` defaults it
- Two test tiers:
  - **Unit tier** (`/test/*-test.js`): self-contained tests that need Redis but not the live server; run in parallel with default `node --test` concurrency. Run with `npm run test:unit`
  - **Integration tier** (`/test/integration/*-test.js`): tests that run against a live EmailEngine server booted by `test/run-tests.js` (api-test, sendonly-test, api-routes-smoke-test, ui-routes-smoke-test); run serially. Server readiness is detected by polling `/health` (`test/helpers/wait-for-server.js`), and the server is killed on exit even when the tests fail or the run is interrupted. Run with `npm run test:integration`
- Test files must be named `*-test.js` - the runner globs only match that pattern, so helper modules (e.g. `test/integration/test-config.js`, `test/helpers/*`) are never executed as tests
- New tests go in `/test` unless they make HTTP requests to the live server, in which case they go in `/test/integration`
- The integration tier is non-hermetic: api-test.js talks to live Gmail/MS Graph and needs credentials from `.env`; failures there are often external-state flakes, re-run before blaming a change
- A test section that needs provider credentials is gated with `skipUnlessEnv('EE_VAR', ...)` from `test/integration/helpers.js`, which returns a skip reason naming the missing variables. Secrets are absent on Dependabot and fork pull requests (`${{ secrets.X }}` expands to an empty string there) and in a fresh checkout, and a section that fails for that reason teaches people to ignore a red integration job
- Run `npm test` for the full suite with linting (unit tier, then integration tier). It lints via `npm run lint:src`, which deliberately covers a narrower set than `npm run lint` (no `test/**`) - CI runs the wider `npm run lint` in its own job
- Every tier flushes its Redis database through the shared `test/helpers/flush-redis.js`, which resolves the database from `NODE_ENV` (db 13 for the test tiers, db 14 for e2e). It uses ioredis, so no `redis-cli` binary has to be on PATH
- **Requiring the `lib/db` chain leaves a process that will not exit.** It opens a Redis client and a BullMQ connection that nothing closes, and since `node --test` waits for every child, one such file used to stall the whole tier with every test reported as passing and no summary - the per-test `--test-timeout` cannot fire, because no test is running. `test/run-tests.js` passes `--test-force-exit` so this cannot happen in either tier (pinned by `test/test-runner-force-exit-test.js`). Individual files still register `test/helpers/redis-teardown.js`, which closes the client gracefully and is what keeps a bare `node --test <file>` usable. **A test file never ends its own process under the runner**: the old `setTimeout(() => process.exit(), 1000)` raced the file's results on their way to the runner (Node's forced exit waits for them, ours did not), and with two files of 20000 tests it left 34194 to 35996 of 40000 counted with the run still green; armed in a suite's own after-hook it could also end the process while later suites were running. Use `exitWhenStandalone()` from `test/helpers/exit-standalone.js`, which exits only when `--test-force-exit` is not in `process.execArgv` (a bare run); `test/test-runner-exit-test.js` keeps every file on it and the results whole. Call it at **module level**, never from inside a test: a `t.after()` registered in a test callback never runs when that test is skipped, which is how `test/account-revoke-on-delete-test.js` came to hang on every dependabot PR (`${{ secrets.X }}` expands to an empty string for a run with no access, so its credential gate went false and the suite skipped). That file no longer has a credential gate at all: the revoke call sends the stored token verbatim to a local capture server, so fixed dummy values exercise the same path and the suite runs everywhere
- **A test file that blocks its event loop escapes both of the guards above.** `--test-timeout` is a timer inside the file's own process, so a synchronous loop or a parked thread is exactly the state in which it cannot fire, and because the run never finishes, `--test-force-exit` never gets its turn either - `node --test` then waits on that child until the CI job is killed, printing no summary and naming no file. This is what took out the unit tier on master at `7e6808be`, which already had both flags. `test/run-tests.js` therefore runs a third guard, `test/helpers/stall-reporter.js`: a reporter runs inside the runner process, whose own event loop is healthy while a child's is not, and it is the only thing there that knows which files have reported. It WRAPS the spec reporter and must stay the runner's only `--test-reporter` - with `--test-force-exit`, a second reporter truncates the run summary (measured at 3410 / 3442 / 3452 tests across five identical runs of this suite, all reporting `fail 0`), and a dropped result can be a failing one. Extend that file rather than adding a reporter beside it, and note that `new spec()` returns its own object, so subclassing it silently discards every override - compose it, as that file does. After `stallTimeout` with no test events from any file it prints the files that never completed and exits non-zero, each with how far it got: no test reported yet (a test is blocked, or the file is still loading), or how many of its tests reported and which one last - when that was its last test, the tests are done and the process never exited. Paths are compared through `realpath`, because the runner reports a file by its real path and macOS keeps its temp directory behind a symlink. Every tier needs a `stallTimeout` (a tier without one silently opts out); the integration tier's must stay above `TEST_TIMEOUT`, since a running test reports nothing until it finishes and a slow live provider would otherwise read as a stall. Pinned by `test/test-runner-stall-watchdog-test.js`. A stalled child is NOT reaped - its process can outlive the run, so a local stall may need a manual kill
- **A result can be lost between a file's process and the runner, with the run still green.** Seen once on 2026-11-02 (macOS, Node 24, the parallel unit tier): a suite of `test/views-csp-guardrail-test.js` reported a subtest's start and nothing further, 28 subtests and the suite's own result never arrived, the file's later top-level tests reported as usual, and the summary counted 29 tests fewer than the next run of the same tier, with `fail 0`. The file on its own reported all 189 results in 20 of 20 runs, so it is the parallel tier that loses them, and the cause was not found. `test/helpers/stall-reporter.js` therefore also tracks every `test:start` against its `test:pass` or `test:fail` (every test reports both, skipped and todo ones included; checked on Node 20, 22 and 24) and, once every event of the run has arrived (its `_flush`), prints the tests still open to stderr and sets the exit code to 1, which `--test-force-exit` honours on all three even when set that late. The decision is deliberately not made at a file's own `test:complete`: on Node 20.19.0 in CI that event arrived before the last suite's start and pass events of `test/api-reference-test.js`, which came a second later and were counted, and a check at that point failed the run for nothing. A lost result fails the run instead of being counted as passed; pinned by `test/test-runner-stall-watchdog-test.js`. If it recurs, the report names the file and the tests. The guard's first full run on Node 20 on macOS reported 119 results lost from the tails of 15 files, with the summary at `fail 0`: a file's process ends through `process.exit()` under `--test-force-exit`, and on macOS a pipe is asynchronous, so what the reporter still had queued for the runner is discarded (on Linux pipes are synchronous and the same run counts everything, which is what CI's Node 20 leg does). Node 24 drains before it exits in all but rare cases. So the unit tier on macOS is only trustworthy on Node 22 or later; the guard turns the Node 20 case into a failure that says so instead of a green run short by a hundred results. Separately, `test/test-runner-exit-test.js` ("the results of every file reach the runner") runs its own nested `node --test` with the tap reporter over 40000 results and asserts 99% arrive; on one CI run the nested run lost its whole summary (`NaN of 40000`), which is that same class of truncation in the nested runner and not a product failure: rerun it
- **A stall report for a file whose last test already reported is usually Node 24 deadlocking in `process.exit()`, not the file.** `--test-force-exit` ends each file through `process.exit()`, which joins V8's background threads, and a concurrent Maglev or Sparkplug compile on one of them can be parked waiting for a garbage collection only the exiting main thread could run (nodejs/node#64274). The process sleeps forever with every test reported, and it struck files that hold no handle at all. `test/run-tests.js` therefore passes `EXIT_SAFE_V8_FLAGS` (`--no-concurrent-recompilation --no-concurrent-sparkplug`), which `node --test` hands on to every file's process; pinned by `test/test-runner-force-exit-test.js`. To confirm a new case, run the files in a Linux container capped at two CPUs until one stalls and take `gdb -p <pid> -batch -ex "thread apply all bt"`: the signature is the main thread in `NodePlatform::Shutdown` / `uv_thread_join` and a `V8Worker` in `CollectionBarrier::AwaitCollectionBackground`
- Read a nested process's output on `'close'`, not `'exit'`: `'exit'` can fire before its stdout has been read to the end, and a summary line, the last thing printed, then goes missing (`test/test-runner-exit-test.js` read a run's count as NaN that way)
- CI (`.github/workflows/test.yml`) runs lint, unit, and integration as separate parallel jobs, so a failed section (usually the flaky integration tier) can be re-run alone via "Re-run failed jobs". The unit job is a matrix: Node 24 and Node 20.19.0 on the current Redis, Node 24 against Redis 7 and against Valkey 8 (ioredis 6 speaks RESP3 by default, so a server answering differently shows up here rather than in a customer's logs), and the require(esm) leg below. `package.json` declares Node >= 20.19.0 while every other job runs 24, and the 20.x leg runs exactly that release, the oldest the dependency tree itself accepts (undici 7 wants >= 20.18.1, html-to-text 10 wants >= 20.19.0); `server.js` warns at startup below it and refuses to start below 20. Anything older is not a meaningful target, since below 20.14 `node --test` has no `--test-force-exit`. A unit test has to pass on both: Node 20 has no `AbortSignal.any()`, its `node --test` runs root-level hooks and mock timers differently, and an unref'd timer can let the event loop drain before it fires (a test file that depends on such a timer keeps a `setInterval` alive for its duration, see `test/webhook-request-test.js`). A separate Node 24 leg runs `npm run test:cjs`, the same tier with `NODE_OPTIONS=--no-experimental-require-module`, so an ESM-only dependency that require(esm) would hide fails there (see "Pure JavaScript only" in CLAUDE.md). The `unit_macos` job runs the tier on macOS with Redis from Homebrew, and `pkg_build_windows` builds the win-x64 binary and runs its CLI smoke test, since both platforms ship as release assets. Every job installs with `npm ci`, the same resolution Docker and the release use, and every Redis service image is pinned to a version tag
- `test/run-tests.js` refuses to start a tier whose API port is already held (`assertPortFree()`), because a stale server on that port would answer `/health` in place of the one the run boots and would be left running on the freshly flushed database. Stop the process holding it first (`lsof -nP -iTCP:7077 -sTCP:LISTEN`)
- **Dovecot tier** (`/test/dovecot/`): live IMAP tests against a real IMAP4rev2 server (Dovecot 2.4+ in Docker), NOT part of `npm test`. Run with `npm run test:dovecot` (needs Docker + local Redis). `test/dovecot/run-dovecot-tests.sh` only starts the container and waits for its greeting, then hands over to `node test/run-tests.js dovecot`, so the tier gets the same Redis flush, port guard, server boot, `--test-force-exit` and stall watchdog as the integration tier, plus the built-in SMTP server enabled through `EENGINE_SETTINGS` (`test/dovecot/listener-settings.js`). CI runs it as the hermetic `dovecot` job in `.github/workflows/test.yml`. Coverage notes in `test/dovecot/README.md`
- **Multi-instance tier** (`/test/multi/*-test.js`): several real EmailEngine processes against one Redis (database 15, flushed by the fleet itself) and an in-memory ImapKit farm, NOT part of `npm test`. Run with `npm run test:multi` (needs only a local Redis). `test/helpers/instance-fleet.js` starts, kills, freezes (SIGSTOP), thaws and restarts instances on ports 7500, 7510, ... (cluster ports one above), each with its own export directory as separate pods would have; `test/helpers/imapkit-farm.js` runs the ImapKit servers (accounts placed round robin, and every user of one server shares its mailbox tree, so an injected message reaches every account on that server); `test/helpers/webhook-ledger.js` records every webhook and matches it to the injection by a token in the subject, so exactly-once is one lookup. Two facts the tests are built around: ImapFlow enters IDLE only after 15 quiet seconds, so a test waits `IDLE_SETTLE` before injecting, and one IMAP session per account is a valid double-ownership check only while idle (under load EmailEngine opens a second session for fetches). `test/run-tests.js multi` runs the files serially with a 10 minute per-test timeout
- **Load and chaos runs** (`test/multi/load/`, `npm run test:load` and `npm run test:chaos`, never in CI by default): standalone programs, allowed to exit on their own (`test/test-runner-exit-test.js` lists them). The ImapKit farm and the webhook ledger run in a child process (`harness-host.js`) so they never share an event loop with the load generator; the report says how busy that process was, and a value near 100 means the harness, not EmailEngine, set the pace. `run-load.js` drives the read, events, mixed and rebalance profiles and reports local and forwarded latency apart (a request is forwarded when the instance it was sent to does not own the account); `run-chaos.js` runs seventeen failure experiments (crash, graceful stop, freeze, slow pod, slow Redis, slow mail server, mail disconnects, peer partition, scale, a restart of the whole fleet, Redis outage, a Redis outage longer than re-registration, Redis reset, one instance cut off from Redis, Redis slow for every instance, two instances crashing together, a donor crashing during a scale-up handoff) through per-instance TCP proxies (`test/helpers/latency-proxy.js`) under background traffic, with an invariant checker: no webhook twice, no message missing at the end, no submission sent twice, no account without a live owner past the failover bound, no instance exiting unless the runner made it, and, while Redis comes back after an outage (given back to the instances one by one, as their clients reconnect on their own schedules), no instance holding more than twice its share. `--mix-minutes N --seed S` adds a replayable random schedule. Reports go to `test/multi/results/` (gitignored). Keep instance uptime under about 9 minutes unless `EENGINE_PREPARED_LICENSE` is set in the environment (the fleet passes it through): without a license an API worker answers every API request with a bare 500 once its periodic license check runs (`runPrechecks()`, every `TLS_RENEW_CHECK_INTERVAL`, ten minutes), and the IMAP workers are suspended after 20 minutes. Both runners ask the fleet itself (`GET /v1/license`, so a license from any source counts), warn when it runs unlicensed, and record the answer in the report. A chaos run whose failures are bare 500s from the one instance it never restarted has hit this, not a cluster fault
- **E2E tier** (`/test/e2e/*.spec.js`): a separate, browser-driven happy-path suite using Playwright (`@playwright/test`), NOT part of `npm test`. It boots a fresh instance (isolated Redis db 14, `config/e2e.toml`, `NODE_ENV=e2e`), drives the admin UI to enable auth + activate a 14-day trial + create an API token, then exercises the REST API end to end against an Ethereal mailbox. Run with `npm run test:e2e` (one-time `npm run test:e2e:install` to fetch Chromium). It runs in its own workflow (`.github/workflows/e2e.yml`, `workflow_dispatch` + push to master) so it is easy to re-run, and is non-hermetic: it needs outbound internet (Ethereal + the postalsys.com trial endpoint). Specs run alphabetically on one shared instance, so a single spec run on its own (`npx playwright test pages-admin`) fails wherever it needs the account that `happy-path.spec.js` registers; set `EE_E2E_STANDALONE=1` to skip those tests instead
- **Mutation testing** (`npm run test:mutation`, `scripts/mutation-test.js`, NOT part of `npm test`): for the pure decision modules whose tests are meant to pin every rule (the learned IDLE interval, the IDLE settings, the tracking flags, the lock wrapper - the `TESTS_BY_FILE` table). Each mutant is one small change to one line (a flipped comparison, a swapped boolean operator, min for max, a dropped negation) run against that file's suites in a private copy of the repository, so the working tree is never touched; it needs the test Redis like the unit tier. A surviving mutant is a rule no test pins, or an equivalent mutant that cannot change any output; judge each by hand, add a test for the real ones, and add a module to the table when it gains rules worth pinning. `--file` limits a run to one module, `--max` samples. Port of ImapFlow's script of the same name

**Route-table guardrails.** Two golden-snapshot tests capture the registered routes in-process against a mock Hapi server (`workers/api.js` itself cannot be imported from a test - it boots a server on require):
- `test/ui-routes-table-test.js` for `lib/routes-ui.js` (admin UI)
- `test/api-routes-table-test.js` for `lib/api-routes/*` - additionally asserts that every `/v1` route declares `auth: { strategy: 'api-token', mode: 'required' }` and carries the `api` tag. A `/v1` route with no `auth` block falls back to `server.auth.default()`, which is the admin session strategy and is only installed when an admin password is set, so a missing auth block is an auth bypass rather than a 401. Adding, removing or renaming a route means updating that test's `GOLDEN_ROUTES`. A new `lib/api-routes` module must be wired into `lib/api-routes/index.js` - that is the single registration point both `workers/api.js` and the capture helper call, so a module missing from it is simply never registered. Do not register `/v1` routes from `workers/api.js` (the guardrail cannot see them) and do not mount them through a Hapi plugin (plugin routes never reach `server.route()`, so they skip the auth and tag assertions; a test fails if route setup registers one).

**OpenAPI document guardrail.** `test/openapi-golden-test.js` records the whole generated document in `test/fixtures/openapi-golden.json` and fails on any drift, because /swagger.json is a published surface (mirrored on emailengine.dev, consumed by Postman and code generators) that no other test would notice changing. A change to a joi schema, a route's `plugins.openapi` block, or `lib/openapi/*` will fail it - re-record with `UPDATE_OPENAPI_GOLDEN=true npm run test:unit` and review the resulting diff as part of the change. The failure message lists the differing JSON pointers rather than dumping the document. The recorded document is byte-identical to what a real server serves apart from `info` and `servers`, and `test/helpers/build-openapi-spec.js` is what keeps it that way - it applies the same server-wide route defaults and the same account schemas and size limits as `workers/api.js`, so anything the document is derived from has to be shared with that helper rather than stubbed in it.

**Do not re-implement production logic inside a test.** Several suites used to carry hand-written copies of the code under test ("simulate what X does"), which cannot fail when the real implementation changes - and had in fact already drifted from it. When a piece of logic is buried in a worker or a class that a test cannot construct, extract it into a small pure module and test that (`lib/smtp-auth.js`, `lib/smtp-message-processor.js`, `lib/response-stream.js`, `lib/email-client/imap/listing-diff.js`, the `is*Error` classifiers in `lib/export.js` are all extracted for exactly this reason).
